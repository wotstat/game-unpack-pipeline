# Скорость скачивания на Aeza, 29 октября 2026

Сравнение выполнялось на почасовых Moscow Shared MSKs-5 с production firewall,
отдельными JIT runner и четырёхчасовым timer самоудаления. Основной контрольный
[run 40793155091](https://github.com/wotstat/game-unpack-pipeline/actions/runs/40793155091)
использовал один pinned Acquisition Plan `wot-eu` / `sd` / `ALL`:

- 16 файлов по 109–146 МиБ, всего 2 182 397 500 байт;
- 4 файла по 568–630 МиБ, всего 2 532 808 412 байт.

Каждый метод скачивал одни и те же файлы в пустой каталог. Размеры, source hash
и SHA-256 проверялись; результаты всех методов должны совпасть. Порядок методов
менялся между повторами. Время включает передачу, `fsync` и проверку целостности;
curl и aria2 дополнительно синхронизируют файлы и каталог перед проверкой. У нашего
клиента внутренняя проверка входит во время передачи. Ни один payload не загружался
в Actions artifacts.

Версии: Python 3.13.14, httpx из `uv.lock`, curl 8.5.0, aria2 1.37.0.
curl запускается в 16 независимых процессах. aria2 получает `-j16`, `--split=1`
либо `--split=16 -x16 --min-split-size=128M`; фактическое разбиение зависит от размера
файла. Исторический downloader использует 16 file workers, исправленный — четыре.

## CDN → диск VM

Медианы двух повторов, МиБ/с:

| Метод | 16 небольших файлов | 4 крупных файла |
| --- | ---: | ---: |
| curl, одно соединение на файл | 71,9 | 93,5 |
| aria2, одно соединение на файл | 205,9 | 95,9 |
| aria2, Range | 234,5 | 215,5 |
| Старый downloader, 16 file workers | 100,1 | 102,1 |
| Исправленный downloader, 4 file workers | 164,5 | 130,9 |
| Исправленный downloader, 16 file workers | 104,6 | 68,7 |
| Исправленный downloader, 1 file worker | 33,8 | 85,9 |

Историческая версия загружена из `2504e2226263bdc72e8d9f1ed0e044b98a575a05`;
benchmark проверяет фактический путь импорта. Исправление вместе с выбором четырёх
file workers дало примерно ×1,64 на небольших файлах и ×1,28 на крупных.
aria2 с Range остаётся быстрее. Эти результаты относятся к указанным подмножествам,
а не к повторной обработке всего клиента.

## Локальный HTTPS → диск и RAM

Источник отдавал из памяти только те же проверенные файлы через `127.0.0.1`.
Отдельный сертификат доверен только benchmark-процессам; публичный ingress
оставался закрытым. Запись повторялась на обычный диск VM и `/dev/shm`.
Медианы двух повторов, включая `fsync` и проверку, МиБ/с:

| Набор и место записи | curl | aria2, Range | Старый downloader | Исправленный downloader |
| --- | ---: | ---: | ---: | ---: |
| Небольшие, диск | 350,0 | 308,3 | 118,7 | 225,5 |
| Небольшие, RAM | 973,5 | 598,3 | 132,5 | 301,5 |
| Крупные, диск | 479,5 | 340,0 | 130,2 | 171,6 |
| Крупные, RAM | 1291,0 | 654,5 | 169,6 | 208,2 |

Ускорение сохраняется без WAN и обычного диска: ×2,28 на небольших файлах и ×1,23
на крупных. Значит, лишние затраты в нашем клиенте были самостоятельным ограничением.
Разница disk/RAM также показывает влияние записи и синхронизации. Исправленный
Python-клиент всё ещё уступает нативным клиентам; паритет не достигнут.

## Причина и исправление

Предыдущий код принимал мелкие raw HTTP/TLS-фрагменты и для каждого выполнял запись,
хеширование и обновление общего прогресса. На быстрых HTTPS-потоках это давало много
вызовов и переключений между потоками. Число file workers также автоматически
наследовало число CPU; на MSKs-5 увеличение с четырёх до 16 оказалось невыгодным.

Теперь фрагменты собираются в ограниченные блоки до 1 МиБ. Неполный блок выдаётся
при следующем чтении после секунды и перед повтором после HTTP-ошибки. Проверки
отмены и idle deadline остаются привязаны к каждому raw read. Range-запись сохраняет
точные смещения и границы сетевых чтений для проверки скорости.
Production download использует четыре file workers и до 12 Range workers;
CPU-стадии сохраняют свои прежние бюджеты.

В локальном HTTPS → RAM контроле небольшого набора медиана CPU-времени снизилась
с 41,62 до 17,84 секунды, а voluntary context switches — с 481 534 до 56 245.
Регрессионные тесты проверяют объединение быстрых фрагментов, прогресс медленных
потоков и точные смещения Range-записи. Итоговый `./scripts/check.sh`: 413 тестов
прошли, 13 opt-in live тестов пропущены; Ruff, mypy, shellcheck и actionlint прошли.

## Ограничения интерпретации

В исходном production-логе run 40736999060 скорость была указана как 30–38 **МиБ/с**,
то есть приблизительно 252–319 Мбит/с. Speedtest измеряет другой маршрут, сервер
и профиль соединений; результат 5 Гбит/с сам по себе не задаёт скорость получения
файлов с игрового CDN с последующей проверкой и сохранением.

Сетевые результаты меняются между повторами. В итоговом прогоне зафиксировано
шесть вариантов DNS-ответов CDN. IP фактического peer для каждого HTTP-запроса
не фиксировался и не закреплялся, поэтому WAN-сравнение не изолирует выбор CDN-узла.
Для причинного вывода об исправлении используются также локальные контроли.
Дополнительный режим четырёх HTTP-процессов
не показал устойчивого выигрыша на CDN и исключён из production-кода и CLI. Результаты
этого эксперимента сохранены в артефактах исторических benchmark runs.

Каждый run занял меньше часа; аренда по €0,53 за час составляет €2,65.
Последний cleanup подтвердил удаление услуги через Aeza API, временного SSH-ключа
и всех runner; финальный запрос GitHub API не нашёл runner ни одного из пяти runs.

Для повторения: `Actions → Benchmark game download`, `repeats: 2` или `3`,
`diagnose: true`, `loopback_control: true`, исторический `baseline_sha` выше.
Это новый платный запуск. Артефакт `download-benchmark-40793155091-1` содержит
72 исходных измерения, SHA-256, манифесты файлов, GNU time и системные samples.
Ранние прогоны до исправления методики не включали явный `fsync` нативных клиентов;
их нативные скорости нельзя напрямую смешивать с итоговой таблицей.
